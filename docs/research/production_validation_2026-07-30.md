## The most important finding: a real gap in `R-QUAL-01`'s own design

Going into this spot-check, the expectation (stated in the approved plan) was that the
zero-coverage veto rule would fire for most or all communes, given the live rainfall
corruption. **It fired for zero.** Two real, distinct reasons, both worth stating plainly:

1. **A corrupted-but-present reading is not "no data."** `R-QUAL-01` checks
   `TerritorySnapshot.has_trigger_signal` — true if *any* of rain/SWI/antecedent/seismic is not
   `None`. Medellín's frozen rain reading is `0.003mm`, a real number, not an absence — so
   `has_trigger_signal` is `True` even though that number is meaningless. The veto is scoped to
   catch **missing** data, not **implausible** data; catching implausible data is
   `domain/quality.py`'s job (via `monitoring/scraper_validator.py`), and nothing before this
   script connected that signal to the inference engine's `TerritorySnapshot.quality_flags`.
2. **Seismic data alone satisfies `has_trigger_signal`.** Commune 12 (La América) has
   genuinely zero rain data of any kind (`trigger=None` from `ml.hazard.hazard_by_commune`
   directly) — but its seismic intensity (0.239) is present, so the OR-condition across all four
   trigger sources is satisfied and the veto still doesn't fire.

**This session's fix, applied in this same script:** it computes `is_frozen_signal()` against
real `rainfall_timeseries` data and populates `TerritorySnapshot.quality_flags` accordingly —
something no code path did before. That correctly lowered every affected commune's confidence
from 0.53 to **0.42** (and La América's, already low at 0.13 due to missing terrain/rain/SWI, is
unaffected since it has no rain rows to flag as frozen in the first place). The confidence
mechanism responds correctly to real corrupted data; the veto rule's scope is narrower than "is
this trustworthy" and that's now a documented, evidenced gap, not a hidden one.

**Recommended follow-up** (not implemented in this session, scoped for a future spec): add a
rule (or extend `R-QUAL-01`) that vetoes specifically on a `"frozen_signal"` quality flag, not
only on total data absence — the real data here shows that's the far more common failure mode in
production today.

## Per-commune neural score is uniformly ~0.000

Every commune except La América (no trigger data at all → `None`) shows `neural_score ≈ 0.000`
today. This is the direct, real consequence of `hazard = √(susceptibility × trigger)`
(`domain/susceptibility.py::hazard_score`) with `trigger ≈ 0` from the frozen rain reading —
exactly the audit's §4.3 prediction ("por construcción, amenaza da 0.000 en todas las comunas"),
now confirmed by actually running the formula against live data rather than reasoning about it.

## What this spot-check does NOT show

- Whether the system would correctly flag a *real* landslide-risk day — there is no way to test
  that without either real historical events (none exist) or waiting for the rain pipeline to be
  fixed and observing a live event.
- Statistical significance of anything — n=21 communes, one point in time, no repeated
  measurement.
- Expert agreement — still requires human DAGRD-affiliated judges (`evaluation/rubric.md`).

## Reproducing this

```bash
cd platform/backend && export PYTHONPATH=.
python -m evaluation.validate_against_production --json-out docs/research/production_validation_<date>.json
```

Requires read access to the production `DATABASE_URL`/`DATABASE_URL_SYNC` (from `.env`, already
configured in this environment). The script only issues `SELECT`s; running it again is always
safe and will reflect whatever the rain signal looks like at that moment.
