# Alternate-data-source validation — 2026-07-30

**Motivation:** the first real-data spot-check
(`docs/research/production_validation_2026-07-30.md`) ran entirely on the live rainfall feed,
which is frozen (20/21 communes), and on zero terrain data (`barrio_terrain` empty) — so the
geotechnical rules (R-GEO-01, R-GEO-02, R-SEIS-01) had almost no chance to be evaluated, let
alone fire. This validation swaps in two **alternate real sources** that don't share those
specific defects, to see whether the rules can fire under genuinely varying, real conditions.

Generated by `platform/backend/evaluation/validate_with_alternate_sources.py`
(`--json-out docs/research/alternate_sources_validation_2026-07-30.json`). Read-only: only
`SELECT`s against Supabase, plus GET requests to Open Topo Data's public SRTM endpoint. No
`INSERT`/`UPDATE`/write path is called anywhere in the script.

## The two alternate sources, and why one was rejected before use

1. **Live SRTM slope** (Open Topo Data, `scraper/terrain_features.py`'s exact pure helpers,
   reused unmodified) — queried for all 21 commune centroids. This is real, live, physical
   terrain data, independent of anything in the database.
2. **Historical rain via `ml_features`, `source='historical_ideam'`** — checked before use and
   confirmed clean: real day-to-day variation, max 104.4mm/day across 1,685 rows, 583 distinct
   values. **Rejected: `source='historical_siata'`** — confirmed still corrupted (max
   92,202mm/day, the exact bug `docs/research/audit-2026-07.md` documented, unfixed) — the
   script does not touch it.

The `historical_ideam` source only covers 3 communes (15, 18, 21), and commune 18's data stops in
2020 (too stale to represent "now" under a 90-day cutoff). So only **communes 15 and 21** get a
real SWI/antecedent-precipitation value computed via `ml.soil_water_index.compute_swi` and
`ml.precip_index.compute_antecedent_precip_index` — both pure functions, run here for the first
time against genuinely real, current daily rain instead of synthetic input.

## Result: real slope data is available everywhere; real rain is not

| Metric | Value |
|---|---|
| Communes with live SRTM slope | **21/21** |
| Communes with real, current (≤90d), non-corrupted rain-derived SWI | **2/21** (15, 21) |
| Max real slope observed | 26.4° (Santa Elena, commune 21) |
| Max real SWI observed | 6.5% (Santa Elena) |
| R-GEO-01 (slope>35° AND rain>120mm) evaluable / fire rate | 10% / **0%** |
| R-GEO-02 (slope>25° AND SWI>80%) evaluable / fire rate | 10% / **0%** |
| R-SEIS-01 (seismic AND SWI moderate) evaluable / fire rate | 10% / **0%** |
| R-HIST-01 fire rate (unchanged from the previous spot-check) | 47.6% |
| `ml_only` vs `neurosymbolic` arm disagreement | 0/21 |

## What this actually shows: the rules are correctly conservative, not broken

Santa Elena (commune 21) is the one case where both a real slope value (26.4°, above R-GEO-02's
25° threshold) and a real SWI value (6.5%) are available simultaneously. **R-GEO-02 correctly
does not fire**, because 6.5% is nowhere near its 80% saturation threshold — even after a real
22.1mm rain event on 2026-06-23, the soil-water index this session actually computed from real
data stays far from "saturated." This is the first time in the project's history that a
geotechnical rule's condition has been evaluated against a real (slope, rain) pair rather than a
synthetic one — and the result is a real, substantive non-fire, not a data-availability gap.
R-GEO-01 requires 120mm of 72h rain; nothing observed in the recent real-data window approaches
that. Neither rule firing here would be correct — Medellín's slopes and this month's rain
genuinely don't cross those thresholds, at least at the coarse, centroid-level granularity this
script queries (see Limitations).

R-SEIS-01 needs a moderately-saturated soil signal alongside seismic data; SWI is only real for
2 communes, and even there it's far below the moderate-saturation band the rule checks for.

## Limitations — read before citing this

- **Slope is centroid-level, not barrio-level.** `scraper/terrain_features.py` samples 5 points
  (center + N/S/E/W at 90m offset) around each commune's single centroid — a coarse
  approximation. `barrio_terrain` (the intended, finer-grained slope source, one row per barrio)
  is still empty in production; a per-barrio slope query would likely find steeper micro-terrain
  than a commune-wide centroid captures, especially in known-hazard barrios. This validation does
  not claim commune-level slope is the right level of analysis — it's the best currently
  available real substitute.
- **Rain coverage is 2/21 communes, one recent window.** This is not a claim that R-GEO-01/02
  never fire in Medellín — only that they didn't fire for these 2 communes in this specific
  30-day real-data window. A wetter month, or coverage of the other 19 communes (which have no
  clean historical rain source at all right now), could change this.
- **Single point in time**, like the previous spot-check — not a repeated measurement, no
  statistical power.
- **No real historical landslide-day labels exist** to confirm the rules would have fired
  correctly on an actual event day; this only tests whether the rule *mechanism* responds to real
  inputs, not whether its thresholds are calibrated against real outcomes.

## Reproducing this

```bash
cd platform/backend && export PYTHONPATH=.
python -m evaluation.validate_with_alternate_sources --json-out docs/research/alternate_sources_validation_<date>.json
```

Requires read access to the production `DATABASE_URL`/`DATABASE_URL_SYNC` and outbound network
access to `api.opentopodata.org` (public, keyless, rate-limited to ~1 req/sec — the script pauses
1.1s between communes accordingly).
