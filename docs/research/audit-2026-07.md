# TEYVA as a neuro-symbolic system: data audit, findings and redesign

**TEYVA — Landslide risk monitoring platform, Medellín**
July 2026

---

## Summary

TEYVA is a landslide risk monitoring platform for Medellín's 19 comunas and corregimientos:
real-time data ingestion (rain, seismic activity, emergencies), a machine learning model for
7-day prediction, an API and a dashboard with a conversational assistant. A recent audit against
the production database found that the classification model reported an AUC-ROC of 0.9435 —
a metric that, on its face, indicated a working system — but was in fact the product of two
independent data failures: the training labels came almost entirely from synthetic events, not
real georeferenced events, and the rainfall signal feeding both the model and the alert system was
corrupted at two separate points in the pipeline.

From those findings we propose a redesign: stop treating TEYVA as "a classifier with business
rules on top" and treat it, explicitly, as **a neuro-symbolic system that integrates
heterogeneous evidence, evaluates the quality and coverage of available data, estimates
territorial vulnerability and quantifies the uncertainty of its conclusions, supporting both
analysis of the current state and exploration of future scenarios.** This is not a rename: each
of those five capabilities has a concrete component, already partially built during the audit,
that is missing only the assembly into a reasoning system rather than loose monitoring pieces.
This document describes that design with the same technical detail as the findings that motivate
it, and states clearly what is implemented today versus proposed. The concrete implementation
plan lives in `specs/` (see `specs/README.md`); this document is the empirical foundation for it.

---

## 1. Context and current architecture

Medellín, given its hillside topography and rainfall regime, has an extensive history of
landslides affecting lives and housing. TEYVA started as an MVP to give Gestión del Riesgo a
unified view of the relevant variables per commune, with two goals: early warning and
explanation.

The architecture combines:

- **Scheduled ingestion** from SIATA (rain, every 30 min), DAGRD (emergencies, hourly), IDEAM
  (weather, every 6h), Medellín Open Data (every 24h) and, more recently, the Colombian
  Geological Survey (seismic activity).
- **A classification model** (XGBoost) combining geographic and precipitation variables to
  estimate 7-day landslide probability per commune.
- **Explicit business rules** (`domain/risk_rules.py`) that translate the model's output into
  risk categories (medium ≥0.35, high ≥0.65, critical ≥0.90) and alert states
  (green/yellow/red). The code itself documents the current design boundary: *"the model never
  learns from these rules; the rules never predict"* — a two-stage hybrid pipeline, not yet a
  neuro-symbolic system in the formal sense, because rule-based reasoning is not integrated into
  training or inference: it is a filter applied afterward.
- **A conversational assistant** with RAG over the system's documentation.
- **Slack alerts** with cooldown, covering rain over threshold, critical risk and scraper
  downtime.

The audit reported below was performed against this production system.

## 2. The model that looked like it worked

The classifier trained and in production reported the following metrics (`ml/models/metrics.json`):

| Metric | Value |
|---|---|
| AUC-ROC (5-fold CV) | **0.9435** |
| AUC-ROC (train) | 0.9443 |
| Precision @ threshold 0.3 | 0.736 |
| Recall @ threshold 0.3 | **0.999** |
| Total samples | 8,429 |
| Positives (landslide within 7-day window) | 26 |
| Positives after SMOTE | 16,806 |
| Features | 7 (centroid lat/lon, density, precipitation, station count) |

At first glance, an AUC of 0.94 with recall of 0.999 suggests a near-ideal model for a
high-false-negative-cost problem like this one. It is exactly the kind of number that gets
reported upward as MVP success.

The audit centered on a simple question rarely asked in projects like this one: **where did the
26 positives come from?**

---

## 3. Finding 1 — The labels were synthetic, not real

Verified against Supabase on 2026-07-29.

The `landslide_events` table contains **6,024 records**, of which:

- **5,844 (97.0%) have no usable location at all** — no coordinates, no barrio, no
  `commune_id`. There is no way to geocode them retroactively because there is no starting data
  in the record.
- **144 (2.4%) are synthetic events** generated by a calibration heuristic called "Snake Line"
  (`scraper/ingest_synthetic_events.py`), explicitly designed to calibrate the hazard index, not
  to train a classifier.
- **36 (0.6%) are real with `commune_id`**, and of those most are not landslides at all: they are
  headlines from the municipal news portal (sports fields, tree planting, water-main works,
  building-code enforcement) captured by an overly loose keyword filter in the DAGRD scraper,
  including exact duplicates.

Defining the training target as *"a real event within the window (reference_date,
reference_date + 7 days]"*, of the 36 real events **none** falls within a feature row for the
same commune in the preceding 7 days: **36 real events → 0 usable positives.** The 144 synthetic
events, under the same definition, produce **901 positives**.

```
Composition of landslide_events (n=6,024)
No location (unusable)                       ████████████████████████████████████████████████ 5,844 (97.0%)
Synthetic (Snake Line)                       █▎                                                  144 (2.4%)
Real with commune (mostly not events)        ▎                                                    36 (0.6%)
```

The **26 positives that actually entered `metrics.json`** came from synthetic events, before the
`landslide_events.is_synthetic` flag (migration `d5e6f7a8b9c0`) that correctly excludes them to
avoid circular contamination was implemented. Once that filter was activated, the positive labels
disappeared — and nothing flagged that silent loss, because `train.py`'s artifact governance
protects production (it doesn't overwrite models if a run doesn't complete), but doesn't notify
when the input dataset collapses.

A second, independent but compounding problem: **6 of the model's 7 features are, in practice,
commune identifiers** — `centroid_lat/lon`, `densidadmax`, `precip_records`, `station_count`, and
a precipitation feature with the corrupted magnitude described in the next section are, for each
commune, nearly constant over time. A model with this input vector doesn't learn temporal risk
dynamics: it learns which communes had events according to the Snake Line heuristic, and
reproduces them. The 0.94 AUC measures how well the model memorizes the heuristic that generated
its own labels, not predictive skill over real landslides.

**Contrast evidence:** a second model trained on the expanded synthetic dataset
(`ml/models/metrics_synthetic.json`, RandomForest, n=6,459, 901 positives, 11 features including
seismic and soil variables) gives an AUC-ROC of **0.6316** — substantially lower, and likely more
representative of the real problem's difficulty once the model can't lean on commune identifiers
disguised as features.

## 4. Finding 2 — The rainfall signal is corrupted in both directions

Verified against Supabase on 2026-07-29. This finding is independent of the previous one and
blocks both the hazard-index trigger and the alert system.

### 4.1 Live path: SIATA → `rainfall_timeseries`

Direct query (2026-07-29) over the table's 8,741 rows:

```sql
SELECT precip_mm, count(*) FROM rainfall_timeseries WHERE precip_mm IS NOT NULL GROUP BY precip_mm ORDER BY precip_mm;

 precip_mm | count
-----------+-------
         0 |  7890
     0.003 |   851
```

The entire series reduces to **exactly two distinct values**. Total accumulated sum across the
20 communes over 25 days: 2.55 mm. Medellín receives between 1,500 and 2,000 mm of rain per year;
not even the driest month historically comes close to 2.5 mm. A single repeated value, instead of
a continuous distribution, is the signature of an aggregation bug, not real meteorology.

We confirmed the cause by inspecting SIATA's actual payload (`Pluviometrica.json`, 228 stations,
captured via a diagnostic workflow because SIATA times out from networks outside Colombia). The
`valor` field each station reports **is not a daily accumulation: it is short-interval rain** —
the SIATA app's "current rain" — with no timestamp or accumulation indicator. In a typical run,
180 of 228 stations report `0.0`, 45 report `-999` (no-data sentinel), and only 3 have a positive
value (max observed: 0.5).

The chain producing the absurd number has three links: (1) the scraper averages across a
commune's stations, and with 180/228 at zero the average dilutes to almost nothing; (2) it rounds
to 3 decimals, collapsing the residual signal to a handful of discrete values; (3) the
accumulation endpoint **sums** those 30-minute short-interval snapshots as if they were daily
accumulation measurements. Additionally, for a phenomenon as localized as the rain that saturates
a specific hillside, averaging per commune is the wrong operation by design: it dilutes exactly
the signal that matters most.

### 4.2 Historical path

The historical rainfall backfill showed, in earlier audits this session, magnitudes in the
opposite direction (up to 92 mm/day sustained, physically implausible), attributed to summing a
cumulative counter instead of differentiating it. The column where that problem was measured
(`precip_sum_mm_day`) **no longer exists under that name in the current schema** of
`ml_features` — the current field is `precip_acum_7d`, which as of this audit is completely
empty (`NULL` across all 16,280 rows). We don't produce a new figure for this path for that
reason: it's an open question about the current state of the historical pipeline, not a closed
finding like 4.1.

### 4.3 Measured consequences

- **`alert_log` empty over the last 30 days.** The rain alert threshold (35 mm) is mathematically
  unreachable with a maximum of 0.003 mm on the live path.
- The soil antecedent moisture index (SWI) is **0 across all 21 communes**.
- By construction, `hazard = susceptibility × trigger` gives **0.000 in every commune**: the
  index is implemented correctly, but its input is zero.

Ingestion itself is reliable — 382 scraper runs over 7 days, nearly all successful. The problem
is not whether data arrives, but what the values it carries mean.

## 5. Immediate design response

Faced with these two findings, the decision was to **give up the supervised classifier as the
source of truth for risk**, rather than trying to patch it with more data or more features — no
new source (seismic, DEM, NDVI) improves a metric whose training target doesn't exist.

The product pivoted toward a **declared index**: `hazard = susceptibility × trigger` (geometric
mean, `domain/susceptibility.py`), with explicitly declared (not learned) weights and an exposed
confidence state: `CALIBRATION_STATUS = "no_calibrado"` in the API and dashboard.

In parallel, `monitoring/scraper_validator.py` was built, detecting the symptoms that led to
these two findings (few distinct values in a series, implausible max within a 14-day window,
daily rain over 400 mm, seismic feed staleness) and reporting silently when everything checks out.

This response is correct but incomplete: today the validator and the declared index are **two
separate systems that don't talk to each other**. The validator detects that the rain is
corrupted; the susceptibility index simply multiplies by zero without knowing why, or
communicating that zero means "no signal" rather than "confirmed zero risk." That gap is the
starting point for the redesign.

## 6. Redesign

**Status: superseded by the spec-driven breakdown in `specs/`.** The architecture proposed from
this audit — heterogeneous evidence integration, data quality scoring, territorial vulnerability
estimation, uncertainty quantification, and scenario exploration — is now specified concretely
across `specs/001-ontology/` through `specs/007-experimental-eval/`. See `specs/README.md` for
the index, sequencing, and status of each component. The `Veto` inference primitive
(`specs/002-rule-engine/`) is the direct answer to the gap described in §5: a data-quality rule
that vetoes a hazard score of zero when the reason is missing signal, not confirmed absence of
risk.

## 7. Other data sources investigated

As part of the same investigation, the seismic sources available to enrich the susceptibility
model were audited:

- The **Colombian Geological Survey (SGC)** feed is not publicly documented — its definition was
  extracted by inspecting the site's JavaScript bundle.
- **USGS**, the usual global seismic source, does not capture the low-magnitude local seismic
  events relevant to Medellín.
- **SIMMA** (Sistema de Información de Movimientos en Masa) has no date field in its records,
  which rules it out as a source of temporal labels, though it is usable as historical event
  density (the `prior_event_density` component).

Both higher-potential improvement paths identified require institutional management, not
engineering work: access to DAGRD's real operational emergency database, and a formal request to
SGC for SIMMA's complete attributes.

## 8. Limitations

- The dataset of real georeferenced events is, in practice, nonexistent (36 usable events, 0
  positives under the training-window definition) — this blocks not only the original classifier
  but any future calibration of the uncertainty formula.
- There is still no reliable source of daily accumulated precipitation per station; the
  historical path (`precip_acum_7d`) is empty in the current schema and the live path has the
  corruption documented in 4.1.
- The current hazard index is explicitly uncalibrated — its weights are declared by expert
  judgment, not fitted against real events.
- The redesign is an architecture proposal, formalized as specs, not code in production at the
  time of this audit.

---

## 9. Comparative landscape: the gap left by undeclared uncertainty

The two findings in this article are specific cases of a more general problem across most
data-driven early warning systems: **almost no system is transparent about uncertainty when data
is missing.** The usual response to an information gap is to "fill it" silently — with satellite
estimation, interpolation between stations, or expert judgment — without telling the end user
that confidence dropped. That is exactly what TEYVA did before this audit: an AUC of 0.94
presented without a caveat, while the label behind that number didn't represent real events.

Systems that are explicit about their reasoning and confidence level do exist — FEWS NET (Famine
Early Warning Systems Network) and the Red Cross's Early Action Protocols are the most mature
examples — but in both cases that transparency is achieved through **narrative reports written by
human analysts**, not through an automated symbolic system declaring its own uncertainty as part
of the data pipeline.

That intersection — **explicit reasoning + automatic confidence declaration in the face of
incomplete evidence, without depending on a human analyst to write it up** — is the space the
redesign in `specs/003-inference-engine/` aims to occupy: per-commune, per-run uncertainty
derived from symbolic data-quality rules is, in essence, the automated version of what a FEWS NET
analyst writes by hand in a paragraph today. This observation is not exhaustively verified
against the literature — it is a reading of the landscape based on the most-cited systems in the
domain, and should be treated as a positioning hypothesis to validate, not a closed result.

## 10. Next steps

See `specs/README.md` for the concrete, ordered task breakdown. In audit-finding order:

1. **Fix the rainfall magnitude** (section 4) — precondition for the trigger, and therefore the
   whole index, to stop reading 0.000 in every commune.
2. **Data quality scoring** (`specs/002-rule-engine/`) — extend `scraper_validator.py` so it
   emits a structured, persisted quality score, not just alerts.
3. **Scenario module** (`specs/003-inference-engine/`, counterfactual endpoint) — invert the
   declared hazard formula analytically. Requires no new data, only the already-declared formula.
4. **Recover or rebuild a real georeferenced event dataset**, possibly via direct access to
   DAGRD's operational database rather than press-headline scraping — precondition for
   calibrating any part of the system, including uncertainty.
5. **Incorporate additional geographic sources** (DEM, NDVI) into the susceptibility component —
   `specs/006-neural-estimators/` task 4, conditioned on a real target existing to validate their
   contribution against.
6. **Evaluate, once the dataset in point 4 exists, whether a strict-sense neuro-symbolic
   architecture is worth it** (logical constraints embedded in training, not just orchestration).

---

## 11. Conclusion

The most useful finding of this work is not a performance number, but a pattern: an ML pipeline
can report excellent-looking metrics (AUC 0.94, recall 0.999) while hiding that the training
target doesn't exist and the input data is corrupted for trivial engineering reasons (rounding,
averaging, summing cumulative counters). Neither problem is visible from the model's metrics
dashboard; both only appear when asking where each number comes from, against the real database,
all the way to the source.

The response we propose is not just declaring uncertainty in a global flag, but building the
system around that declaration: a symbolic layer that evaluates each source's quality, an
evidence layer that doesn't depend on a single fragile model, a territorial vulnerability index
whose weights are auditable, and — because those weights are explicit rather than learned — the
ability to explore future scenarios by construction, not as a feature bolted on afterward. That
is the neuro-symbolic system this article proposes, and the specs in `specs/` are its concrete
starting point, not an aspiration: much of it already exists in the repository, it only needs
assembling.
